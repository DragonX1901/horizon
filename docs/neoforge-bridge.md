# NeoForge 1.21.1 bridge

Goal: Horizon players join a **NeoForge 1.21.1** server running real Java mods. The mods' logic
runs on the server in Java. The Horizon client draws what the server sends and loads blocks, items,
models and textures from the mod jars.

Java mod jars still don't run inside Horizon ([mods.md](mods.md)). This bridge avoids that problem
by keeping the Java code on the server.

```
Horizon client ──777──▶ horizon-neoforge-bridge ──767──▶ NeoForge 1.21.1 server
 (26.3 engine)            translates packets               + horizon_bridge companion mod
                          answers NeoForge's handshake     + any mods
                          remaps registry ids
```

## Pieces

| Piece | Where | What |
|---|---|---|
| Bridge | `crates/horizon-neoforge-bridge` | The proxy. `ids_767.rs` holds the 1.21.1 packet ids, generated by `tools/neoforge_bridge/gen_ids_767.py` from the 1.21.1 data generator's packets report. `neoforge.rs` holds NeoForge 21.1's configuration payloads. `session.rs` runs one player's connection. `facts.rs` holds what the server synced. |
| Companion mod | `mods/horizon-bridge-neoforge` | A server-side NeoForge mod. When a client offers `horizon_bridge:hello`, it negotiates that client as having every channel the server registers, so mods with required channels accept the bridge. It also sends `horizon_bridge:block_states`, the full block-state table (block, properties, value order, state ids), which Java code defines and no data file contains. Clients never install it. |
| Build | `tools/neoforge_bridge/build_companion.py --server-dir DIR` | Compiles the mod with `javac` against an installed NeoForge server's libraries. No Gradle needed. |

## Run it

```sh
# server: NeoForge 21.1.x, online-mode=false for now, companion mod in mods/
python3 tools/neoforge_bridge/build_companion.py --server-dir ~/neoforge-server
cp target/horizon-bridge-neoforge-0.1.0.jar ~/neoforge-server/mods/

# bridge, next to the player
cargo run -p horizon-neoforge-bridge -- --server my.server:25565 --listen 127.0.0.1:25566 --dump captured/
# Horizon: Multiplayer → add 127.0.0.1:25566
```

`cargo run -p horizon-neoforge-bridge --example bridge_probe` joins the bridge the way the client
does and prints the result.

## How NeoForge 21.1 negotiates, and what the bridge answers

Taken from NeoForge's 1.21.1 branch (`ServerConfigurationPacketListenerImpl.java.patch`,
`NetworkRegistry`, `ConfigurationInitialization`).

1. When configuration starts, the server sends `minecraft:unregister`, `minecraft:register`, an empty
   `neoforge:register` query and ping 0.
2. The bridge answers the query with NeoForge's own channels (all version `"1"`, optional) and
   `horizon_bridge:hello`. With the companion mod installed, the server then counts every channel it
   registers as present on the client.
3. The server sends `neoforge:network` with the negotiated setup, then vanilla configuration. Before
   the tags, it sends NeoForge's tasks: frozen registry sync (`frozen_registry_sync_start`,
   `frozen_registry` × n, `frozen_registry_sync_completed`, which the bridge echoes), known data maps
   (the bridge accepts all of them), extensible enums and feature flags (the bridge acknowledges
   both), and config files.
4. `neoforge:split` parts are reassembled into whole packets.
5. `select_known_packs`: the bridge claims only `minecraft:core 1.21.1`. Vanilla entries then arrive
   as bare names, and modded entries arrive with their full data.
